# AGENTS.md — SmartDash

ESP32-S3 прибор Honda Dunk AF78 на PlatformIO/Arduino. Один env: `jc3636w518c`.
Подробности есть в `README.md` и `docs/SMARTDASH_DEV.md`; здесь только неочевидное.
Комментарии и документация в репозитории — на русском.

## Сборка, прошивка, проверка

- `pio` **не в PATH**. Использовать полный путь:
  - сборка: `~/.platformio/penv/bin/pio run -e jc3636w518c`
  - прошивка: `~/.platformio/penv/bin/pio run -e jc3636w518c -t upload`
- Порт определяется автоматически (macOS: `/dev/cu.usbmodem*`, Linux: `/dev/ttyACM0`).
  На Linux группа `dialout` есть в `/etc/group`, но в текущей сессии её может не быть:
  при `Permission denied` прошивать через `sg dialout -c '~/.platformio/penv/bin/pio run -e jc3636w518c -t upload'`.
- Тестов, CI, линтеров и task-runner нет (`test/` пуст). Проверка = успешная сборка;
  поведение на железе проверяется отдельной прошивкой.
- Предупреждения LovyanGFX про deprecated `drawString` при сборке — ожидаемы, не ошибки.
- Коммиты сразу пушатся в `origin/main`. Статус смотреть через `git status -sb`
  или `git branch --show-current`.
- **Не заливать на плату и не коммитить без явной просьбы пользователя** — перед этим
  он каждый раз даёт отдельное разрешение.

## Потоки и порядок инициализации

- BLE (скан, коннект, GATT discovery, AT-init, опрос OBD) живёт в `elmTask` на **core 0**.
  `loop()` (UI + web + USB Serial) — на core 1 и не должен ждать радио-операций.
- Публичные `elm_*()` только выставляют volatile-флаги; разбирает их `elm_loop()`.
  Не вызывать NimBLE API из UI/web: блокировки до сотен мс замораживают тач.
- Порядок `setup()`: `storage_init` → display → ui → web → elm. Менять нельзя: NVS должен
  быть открыт до чтения сохранённого адреса ELM.

## Диагностика (не через Serial)

- `Serial.printf` по USB CDC блокирует ~800 мс, поэтому `SD_LOG` по умолчанию no-op;
  включать только `-DSMARTDASH_SERIAL_DEBUG=1` в `build_flags`.
- Постоянный журнал — LittleFS `/elm.log` + `/elm.prev.log`, ротация при 1 МБ,
  префикс строки `bN tS.mmm`. Пишется всегда, независимо от дебага.
  Чтение: USB Serial `log` / `log all` / `clear`; HTTP-страница `/log` и текст
  `/elm-log`, `?all=1`, `?clear=1` (после очистки — редирект на `/log?cleared=1`).
- Раз в `PERF_REPORT_MS` (2 с) в тот же журнал пишутся строки `PERF`: среднее/макс
  по `ui` (с подучастками setup/input/draw), `elm`, `web`, `serial`, стоимость самой
  записи (`log`) и максимальный интервал между входами в `loop()` (`period`).
  Источник — `src/perf.cpp`; запись лога попадает в `period`, а не в длительность UI.
- `src/storage.cpp` держит `/elm.log` открытым между вызовами `storage_log()`:
  open/close на каждую строку стоили десятки мс и давали просадку `period`.
  Чтение/очистка журнала делают `flush()`/close под `logMutex`; при резком обесточивании
  могут потеряться последние неслитые строки (буфер LittleFS), это допустимо.
- NVS namespace `smartdash`: `last_elm`, `last_elm_type`, `drag_last`,
  `drag_best_60/80/100`, `drag_run_seq`, плюс пользовательские `cfg_*` из `src/settings.cpp`
  (включая `cfg_web_enabled` — состояние кнопки WEB, дефолт выключено).
  Старый общий `drag_best` переносится только при совпадении цели.
- Пины и константы — только в `include/config.h`. Веб AP в одном стиле отдаёт корень
  `/` с кнопками SETTINGS / DRAG LOG / ELM LOG, форму `/settings` (POST + PRG-редирект),
  страницу `/drag` со списком CSV заездов (`/drag-csv?n=...`, `&dl=1` — скачивание)
  и страницу журнала `/log` (текст — `/elm-log`); `DNSServer` в режиме catch-all плюс
  редирект probing-путей дают captive portal — телефон сам открывает корень.
  WEB поднимают/опускают кнопкой на экране Settings: `web_set_enabled()` останавливает
  сервер, DNS и радио, состояние пишется в `cfg_web_enabled` и восстанавливается при
  загрузке. Экран Settings показывает текущие значения и кнопку WEB, поля правит веб.
  Дефолты — в `config.h`, сохранение — в NVS под `cfg_*`. Инвентарь — `docs/SETTINGS.md`.

## BLE/ELM: проверенные грабли

- ESP32-S3 не имеет Bluetooth Classic — нужен BLE-ELM327.
- Полный GATT discovery обязателен. Приоритет характеристик: `FFF1=Notify / FFF2=Write`;
  для Vgate/iCar — профиль `18F0` (`write=2AF1`, `notify=2AF0`).
  Fallback `write=0x2a00` / `notify=0xfff1` **не работает**: AT-команды не доходят
  и инициализация висит на `Initializing ELM...`.
- Сначала пробуется адрес из NVS с типом адреса, ретраи 2→60 с; после трёх неудач —
  поиск любого совместимого адаптера.
- Сканирование/подключение идёт в фоне независимо от того, открыт экран ELM Monitor
  или нет; повторный scan запускается только тапом `Scan`, не входом на экран.
- Экран ELM Monitor до инициализации показывает список найденных устройств, после
  `INIT_DONE` — данные активного адаптера (`elm_get_connected()`): имя, MAC, тип адреса,
  протокол, RSSI и uptime. Имя сохраняется в NVS (`last_elm_name`); при подключении
  по сохранённому MAC RSSI неизвестен (-127). Тапы по списку при подключении игнорируются.
- Опрос разделён: `010C0D` (обороты+скорость) — основной; `0105` и `ATRV` чередуются
  раз в секунду. Паузы после ответа нет: `>` уже означает готовность, следующий запрос
  уходит на такте `elmTask` (~2 мс). Если клон отвечает по таймауту или без `41 0C`,
  пауза растёт 8→…→120 мс и медленно уменьшается после серии чистых ответов.
  Откат на `010C/010D/0105/ATRV` — только при паузе 120 мс и трёх ответах без `41 0C`.
  Не возвращать фиксированную паузу после каждого запроса и не ставить температуру
  в общий пакет — это главная причина «скачков» показаний.
- На этом адаптере `010C0D` **не поддерживается**: в ответе приходит `7F 01 12`,
  поэтому `useMultiPid=false` и опрос идёт раздельными `010C`/`010D`. Race-режим
  обязан уважать этот флаг (и уметь откатиться прямо во время замера): если слать
  `010C0D` в Drag, `dash` не обновляется и экран показывает последнее значение
  с дашборда. Сэмпл в раздельном режиме отдаётся после ответа `010D`.

## UI и замер разгона

- Навигация по осям: с Dash свайп вверх — ELM Monitor, вниз — экран настроек;
  с ELM вниз — назад, с настроек вверх — назад. Влево/вправо — Dash↔Drag.
  На Drag вертикальные свайпы игнорируются, двойной тап (два тапа за 400 мс)
  сбрасывает замер: незавершённый CSV удаляется, автомат возвращается в ожидание
  холостых. BOOT переключает Dash/Drag и закрывает модальные экраны.
  Настройки редактируются только веб-формой в
  `web_loop()` (та же UI-задача), пишутся в NVS и через `ui_settings_changed()`
  заставляют `ui_loop()` перерисовать статику целиком; `elmTask` их не читает.
- Дашборд обновляется инкрементально: дуга RPM заливается только в изменившемся
  интервале, на панель через `setClipRect()` + `pushSprite()` уходят только «грязные»
  прямоугольники. Полный кадр — только при смене экрана. Не вызывать `flush()` на
  каждый тик данных: это полные 252 КБ из PSRAM по QSPI.
- Стрелка RPM рисуется по сглаженному `shownRpm`, а не по сырому `cur.rpm`:
  экспоненциальное сглаживание каждый тик UI с τ=250 мс на рост и τ=600 мс на
  падение, поэтому джиттер OBD не дёргает дугу, а после резкого сброса стрелка
  плавно возвращается к текущему значению. На свежей статике/смене экрана
  `shownRpm` сразу приравнивается к цели.
- `src/dragrace.cpp`: холостые 1500–2500 об/мин 800 мс → скачок оборотов лишь
  подтверждает старт, отсчёт идёт от интерполированного пересечения 3 км/ч
  (защита от газовки на месте).
- Сэмпл `DashData::t_ms` = середина интервала запрос→ответ (`t_tx_ms`/`t_rx_ms`),
  а не время парсинга; для таймаутов и служебных снимков midpoint не применяется.
- Сырые сэмплы от Armed до финиша пишутся в отдельный CSV-файл на каждый заезд:
  `/drag/0001_t60_b52.csv` (номер, цель, загрузка), колонки
  `t_ms,tx_ms,rx_ms,rpm,speed_kmh,event,total_cs,splits`. Последняя строка —
  `RESULT` или `ABORT:<причина>` со splits. Держим последние 20 заездов; файлы отдаёт
  веб-страница `/drag`: кнопки VIEW / DOWNLOAD / DELETE в один ряд на заезд,
  `/drag-view?n=<индекс>` рисует график скорости и оборотов со шкалой времени;
  таблица — только RPM/SPEED/TIME, нулевые сэмплы пропущены (один до старта),
  дробная часть скорости оценена по сглаженным оборотам внутри интервала с
  одинаковой целой скоростью: наклон берётся по окну ±10 сэмплов (не по разности
  соседних групп — джиттер оборотов давал выбросы), дробь ограничена [0,1),
  затем всё сглажено и интерполировано на сетку 50 мс; итоговая строка показывает
  максимум скорости и момент его достижения,
  `/drag-csv?n=<индекс>&dl=1` — скачивание, `/drag-delete?n=...&name=...` — удаление.
  В `/elm.log` остаётся только итог `DRAG <target>,...`; best — отдельно на каждую цель.
- Симуляция заезда без адаптера (режим `sim` через USB Serial). Сначала выйти на экран
  Drag (BOOT или свайп влево/вправо) — иначе сэмплы уйдут только на дашборд. Каждая
  строка `sim ...` публикует **один** снимок с `t_ms = millis()+10`; интервал между
  строками и есть период опроса. Шаг 100 мс достаточно, чтобы отработали все пороги.
  Во время подачи строк обязательно читать USB Serial: `sim` печатает каждую строку,
  и без чтения буфер CDC заполняется, `Serial.printf()` блокирует UI-задачу и
  искажает интервалы (в логе это видно как `serial max` в сотни мс).
  Основной сценарий — реалистичный: холостые 3–4 с, набор оборотов 2–3 с,
  разгон 0→76 км/ч за 14–17 с, плавный сброс оборотов и скорости 4–5 с.
  Шаг 100 мс. Порядок фаз:

  1. Холостые `sim rpm=1800 spd=0` 3.5 с (35 сэмплов) → состояние `ARMED - GO!`.
  2. Поднять обороты 1800→5000 за 2.5 с при `spd=0`. Скачок оборотов лишь
     подтверждает старт: пока скорость <3 км/ч, таймер не идёт.
  3. Разгон: скорость 0→76 км/ч с повторами сэмплов (OBD отдаёт целые км/ч),
     обороты одновременно растут 5000→8000. Пересечение 3 км/ч запускает таймер,
     70 км/ч наступает примерно через 15 с.
  4. Плавный сброс `rpm 8000→0` и `spd 76→0` за 4.5 с. Финиш по сбросу оборотов
     наступит через ~0.8 с от начала сброса (`rpm ≤ peak−800`, то есть ≤7200);
     оставшиеся команды уйдут только на дашборд, в CSV они не попадут.
  5. `sim off`.

  После `Finished`/`Aborted` автомат сам не перезапускается: перед следующим
  заездом нужно выйти с экрана Drag и вернуться обратно (BOOT дважды или свайп
  влево/вправо). Иначе сэмплы пойдут только на дашборд и нового `DRAG` не будет.

  Чтобы заезды немного отличались друг от друга, сценарий рандомизирует:
  холостые 1700–1900 об/мин, пик 7800–8200 об/мин, конечную скорость 74–77 км/ч,
  джиттер оборотов ±1.5% и паузы между сэмплами ±5 мс. Смещение скорости
  (`speed_bias`) выбирается один раз на заезд и остаётся постоянным — так
  монотонность сохраняется и пересечения отметок не пропускаются.

  Ожидаемый результат: экран `WAIT IDLE RPM → ARMED - GO! → RUNNING → DONE`,
  в `/elm.log` строка `DRAG 70,...` с временем ~15–16 с (не 100! цель фиксации —
  последняя пересечённая отметка 70 км/ч, потому что заезд закончен сбросом
  оборотов), а в вебе `/drag` — новый CSV с последней строкой `RESULT`. Если
  надо дойти до цели 100, доводите скорость до 100 км/ч **до** сброса оборотов.

  Готовый сценарий (порт поправить при необходимости):

  ```bash
  ~/.platformio/penv/bin/python - <<'PY'
  import random, serial, time
  s = serial.Serial('/dev/cu.usbmodem1101', 115200, timeout=0)

  idle_rpm = random.randint(1700, 1900)
  peak_rpm = random.randint(7800, 8200)
  top_speed = random.randint(74, 77)
  speed_bias = random.uniform(-1.0, 1.0)  # постоянный на заезд, сохраняет монотонность

  def sim(rpm, spd, pause=0.1):
      rpm = max(0, int(rpm * random.uniform(0.985, 1.015)))
      spd = max(0, min(99, int(spd + speed_bias)))
      s.write(f'sim rpm={rpm} spd={spd}\n'.encode())
      s.read_all()  # обязательно: иначе буфер USB CDC заполнится и заблокирует устройство
      time.sleep(max(0.08, pause + random.uniform(-0.005, 0.005)))

  # 1. Холостые ~3.5 с -> ARMED
  for _ in range(random.randint(34, 36)): sim(idle_rpm, 0)

  # 2. Набор оборотов до 5000 за 2.5 с, пока скорость нулевая
  for i in range(1, 26):
      sim(idle_rpm + (5000 - idle_rpm) * i // 25, 0)

  # 3. Разгон 0 -> 74..77 км/ч за ~17 с, обороты 5000 -> 7800..8200
  samples = sum(3 if spd % 4 == 0 else 2 for spd in range(0, top_speed + 1))
  i = 0
  for spd in range(0, top_speed + 1):
      # повторы дают ~0.45 км/ч за такт 100 мс при целочисленном OBD
      for _ in range(3 if spd % 4 == 0 else 2):
          rpm = 5000 + (peak_rpm - 5000) * i // (samples - 1)
          sim(rpm, spd)
          i += 1

  # 4. Плавная остановка 4.5 с (финиш наступит в начале сброса)
  for i in range(1, 46):
      sim(round(peak_rpm * (1 - i / 45)), round(top_speed * (1 - i / 45)))

  s.write(b'sim off\n')
  s.close()
  PY
  ```

  Для быстрой проверки самого автомата можно сжать фазы: 12 холостых сэмплов,
  скачок до 8000 об/мин, 13 шагов скорости 3…74 км/ч и короткий сброс — заезд
  займёт ~1.2 с, но все переходы состояний отработают.

## Внешний референс

- `erdemerciyas/ESP32-S3-OBD2` (AURA v1.2.1): их ROLL — не бортовой таймер, а поток
  телеметрии + анализ на Android (GNSS телефона + IMU QMI8658). На ESP нет ни таймслипы,
  ни обратного отсчёта; результат считает приложение.
- Переносимые идеи уже внедрены: midpoint `tx/rx`, сырая скорость без EMA, best per target.
  Приложение для телефона не планируется — phone-bridge и синхронизацию часов не портировать.
  GNSS/IMU-слияние, автокалибровка OBD по GPS и уклон без доп. датчиков не переносятся;
  реалистичная точность OBD-only — около ±0.2–0.5 с.
